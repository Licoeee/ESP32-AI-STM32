# 阶段 1 协议说明与运行步骤

## 1. 目标

第一阶段的目标是先把整条最小闭环跑通：

- ESP32 通过 Wi-Fi 连接网络
- 麦克风采集原始 PCM 音频
- 通过 WebSocket 流式上传音频
- 本地语音识别服务返回识别结果
- ESP32 串口打印识别文本
- 后续切换成现成服务时，只改地址和少量协议字段

这一阶段强调两点：

1. **实时性**：采集与网络发送分离，使用 RTOS 任务保证音频采集稳定
2. **可切换性**：后续更换识别服务时，不改采集层结构

---

## 2. 系统结构

ESP32 端当前采用以下结构：

- `wifi_init_sta()`
  - 只负责 Wi-Fi STA 连接
- `audio_service_start()`
  - 只负责启动音频服务
- `audio_service_set_asr_ws_url()`
  - 只负责设置识别服务地址

音频服务内部采用 RTOS 拆分任务：

- **采集任务**
  - 从 I2S 麦克风读取 PCM
  - 将音频帧写入队列
- **发送任务**
  - 从队列中取出 PCM
  - 通过 WebSocket 批量发送给服务端
- **回包处理**
  - 接收服务端文本结果
  - 提取 `text` 字段并打印到串口

---

## 3. 音频采集参数

当前默认参数如下：

- 采样率：`16000 Hz`
- 位深：`16-bit`
- 声道：`1`（单声道）
- 数据格式：`PCM little-endian`
- 每帧采样数：`320`

这些参数的意义：

- `16kHz`：适合常见语音识别服务
- `16-bit`：兼容性好，便于直接传输
- 单声道：降低带宽与处理开销
- `320` sample/帧：便于做分批上传和低延迟处理

---

## 4. 硬件引脚

当前代码默认使用以下 I2S 引脚：

- `BCLK = GPIO16`
- `WS = GPIO17`
- `DIN = GPIO15`

如后续硬件接线变化，只需要修改音频服务中的引脚定义即可。

> 注意：修改引脚前请先核对板级文档，避免与其他外设冲突。

---

## 5. WebSocket 协议

### 5.1 连接地址

本地开发阶段默认地址：

```text
ws://127.0.0.1:8000/asr/ws
```

后续切换到现成服务时，只需要替换成实际地址即可，例如：

```text
ws://your-server-domain:port/asr/ws
```

### 5.2 建连后的握手消息

ESP32 在 WebSocket 连接成功后，会先发送一条 JSON 文本，说明音频流参数：

```json
{"type":"start","sample_rate":16000,"bits":16,"channels":1,"format":"pcm_s16le"}
```

### 5.3 音频数据消息

握手完成后，ESP32 按二进制消息发送原始 PCM：

- 数据类型：`int16_t` PCM
- 发送方式：WebSocket binary frame
- 发送策略：多个音频帧批量发送

### 5.4 服务端返回消息

建议服务端返回 JSON 文本，格式如下：

```json
{"type":"result","text":"识别内容"}
```

ESP32 端会优先解析 `text` 字段；如果没有该字段，则直接打印原始返回内容。

---

## 6. 建议服务端行为

为了保证后续切换顺利，本地或云端服务建议支持以下行为：

1. 接收 WebSocket 连接
2. 识别 `start` 握手消息
3. 持续接收 PCM 二进制帧
4. 将音频送入 ASR 引擎
5. 返回 JSON 文本识别结果
6. 支持断线重连

建议服务端至少返回以下事件类型：

- `start`：开始一轮音频流
- `result`：识别结果
- `error`：错误提示
- `end`：一次识别结束

## 7. 启动本地识别服务

这里推荐先用一个**本地 Python WebSocket 服务**做联调占位。这样可以先验证 ESP32 端的采集、上传、回包链路，后续再把服务端替换成真正的 ASR 引擎。

### 7.1 环境准备

安装 Python 3.10+，然后安装依赖：

```bash
pip install websockets
```

### 7.2 新建本地服务文件

在电脑上新建一个文件，例如：

```text
asr_server.py
```

写入下面的示例代码：

```python
import asyncio
import json
import websockets

HOST = "127.0.0.1"
PORT = 8000
PATH = "/asr/ws"

async def handler(websocket):
    print("client connected")
    pcm_bytes = 0
    frame_count = 0

    async for message in websocket:
        if isinstance(message, str):
            print(f"text from client: {message}")
            continue

        pcm_bytes += len(message)
        frame_count += 1
        print(f"received pcm bytes={len(message)}, total={pcm_bytes}, frames={frame_count}")

        if frame_count % 20 == 0:
            result = {
                "type": "result",
                "text": f"本地服务收到音频，累计 {pcm_bytes} 字节"
            }
            await websocket.send(json.dumps(result, ensure_ascii=False))

async def main():
    async def ws_handler(websocket, path=None):
        request_path = getattr(websocket, "path", path)
        if request_path != PATH:
            print(f"invalid path: {request_path}")
            await websocket.close()
            return
        await handler(websocket)

    async with websockets.serve(ws_handler, HOST, PORT):
        print(f"ASR server listening on ws://{HOST}:{PORT}{PATH}")
        await asyncio.Future()

if __name__ == "__main__":
    asyncio.run(main())
```

### 7.3 启动服务

在该脚本所在目录运行：

```bash
python asr_server.py
```

启动成功后，终端会显示：

```text
ASR server listening on ws://127.0.0.1:8000/asr/ws
```

### 7.4 服务端工作方式

这个本地服务的作用是：

- 接收 ESP32 发来的 WebSocket 连接
- 打印握手文本
- 接收 PCM 二进制帧
- 每累计一定帧数后返回一个 JSON 文本结果

它是一个**联调占位服务**，不是正式 ASR 引擎，但足够用来验证整条链路是否打通。

### 7.5 后续替换为真实识别服务

当你接入真正的识别服务时，只需要：

- 保持同样的 WebSocket 路径或调整 ESP32 端 URL
- 保持握手 JSON 字段兼容
- 保持返回 JSON 中有 `type=result` 和 `text`

这样 ESP32 端就几乎不需要改动。

## 8. 运行步骤

### 8.1 启动本地识别服务

先启动本地 WebSocket ASR 服务，确保监听地址为：

```text
ws://127.0.0.1:8000/asr/ws
```

服务端至少要能：

- 接收 WebSocket 连接
- 接收 PCM 数据
- 返回文本结果

### 8.2 配置 ESP32

ESP32 端默认使用本地地址：

```c
audio_service_set_asr_ws_url("ws://127.0.0.1:8000/asr/ws");
```

后续如果要切换到现成服务，只改这一行即可。

### 8.3 连接麦克风

按当前默认引脚接线：

- `GPIO16` -> 麦克风 `BCLK`
- `GPIO17` -> 麦克风 `WS`
- `GPIO15` -> 麦克风 `DIN`

### 8.4 编译和烧录

在 ESP-IDF 环境下编译并烧录工程。

### 8.5 观察串口日志

正常运行时，串口应能看到：

- Wi-Fi 连接成功
- WebSocket 连接成功
- 麦克风 I2S 初始化成功
- 识别结果文本打印

---

## 9. 验证顺序

建议按下面顺序验证，避免把问题混在一起：

### 第一步：Wi-Fi

- 确认能正常连接路由器
- 确认原有 STA 流程不受影响

### 第二步：I2S 麦克风

- 确认能持续读取 PCM
- 确认不死机、不复位

### 第三步：WebSocket 连接

- 确认能连接本地服务
- 确认断线可自动重连

### 第四步：PCM 上传

- 确认 PCM 二进制能正常发送
- 确认服务端能收到有效音频

### 第五步：识别结果回传

- 确认服务端返回文本
- 确认 ESP32 串口能打印识别内容

---

## 10. 后续切换到现成服务时的最小改动

后续切换服务时，通常只需要改三类内容：

1. **WebSocket URL**
2. **服务端返回 JSON 字段**
3. **认证相关字段**，例如 token 或 header

采集层、队列层、任务结构都不需要调整。

---

## 11. 当前 ESP32 端职责边界

为了让代码长期可维护，当前建议保留以下职责边界：

### `wifi_init_sta()`

- 只处理 Wi-Fi 连接

### `audio_service_start()`

- 只处理音频采集、缓冲、上传、回包输出

### `audio_service_set_asr_ws_url()`

- 只处理识别后端地址切换

---

## 12. 一句话总结

本阶段的核心是：**保持 Wi-Fi 不变，用 RTOS 拆分音频采集与上传，通过 WebSocket 对接本地 ASR 服务，并把识别文本稳定打印到串口；后续切换真实服务只改地址和返回格式。**
